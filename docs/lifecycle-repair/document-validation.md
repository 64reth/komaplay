The rules live in `router-app/lib/editorial-validation.ts`. Zod schemas produce `{key, sectionId, field, code, message}`; server-only availability errors additionally carry the contributor's rejected address so stale messages disappear when it is edited. Section IDs are stable; visible position numbers are recalculated from current order. Both the browser and server use the same rules. Category availability is supplied as context; address uniqueness is determined by the database and translated into this same contract.

## Drafts and persistence

Save Draft accepts missing or unsuitable editorial content. The original title, address, summary, media details, format and ordered section JSON are retained in `working_document.composer`, an additive property in the existing JSON document. Canonical feature metadata uses a safe private title/address where database constraints require it. These values do not replace the contributor's entered values when reopening. Existing documents without the extra property continue through the original module/body conversion.

Normal submission first saves the current draft. If requirements remain, it returns the saved ID and draft/revision state, a structured issue list and `Your draft is safely saved, but it hasn’t been submitted yet.` If everything is ready, the existing submit RPC changes lifecycle to submitted. No new database migration, RLS change or public renderer change is needed. The existing timestamp trigger records first successful submission and retains it across revisions. A later submit failure leaves the saved draft and ID intact.

If a requested address is already used, a narrowly handled unique-address conflict retries the draft save with a private internal address, preserves the requested address in JSON, and reports an actionable address issue on submission. No other database failures are retried or shown verbatim. Invalid category input is retained in JSON while the database uses its existing default-category behaviour for draft storage.

Permissive does not mean unlimited/unstructured input: transport still requires a recognised flat section shape, unique stable IDs, valid panel ID and bounded strings (up to 1,000,000 characters) / at most 500 draft sections. These safeguards protect the request/storage boundary. Submission enforces the smaller existing editorial limits above. Draft save failures never falsely claim the latest edits are saved; the contributor is told to keep the page open and retry.

## Feedback and accessibility

- Requirement count and every corrective action appear beside the controls before submission.
- Failed submission announces an error summary, retains all entered content/order, focuses the first currently invalid field, and marks every invalid field and section.
- Each field uses `aria-invalid` and an `aria-describedby` reference to its own message. Summary links focus the same stable target. Reordering/deletion updates labels without stale ID references.
- No browser-native required-field popup prevents an incomplete draft save: the form uses the shared guidance instead.
- Save, blocked submission and submitted confirmation have distinct styles and wording. Success says `Everything looks ready. Your panel has been submitted for review.` and immediately shows the Submitted badge.
- Unexpected submission failure after a confirmed save says: `Your draft is still safe, but we couldn’t submit it just now. Please try again. If the problem continues, contact the KOMA team.` If saving itself failed, the message explicitly says the latest changes could not be saved. Raw database, transport and schema messages never reach the contributor.
